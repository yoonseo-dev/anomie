## 1. 기획 단계

- 서비스명: Anomie / 플랫폼: Flutter(모바일) + Node.js(백엔드)
- **앱 정체성 (10-10)**: "이론(책)과 현실(뉴스)을 개념으로 잇는 개념 노트". 뉴스 스크랩을 유지하며 독서 앱으로 전환하지 않음 (독서 기록 앱은 경쟁이 심하고, 책과 뉴스가 개념으로 이어지는 구조가 차별점)
- 핵심 컨셉: 뉴스 URL 또는 책 사진을 스크랩하면 Claude가 개념 태그를 제안하고, 사용자가 승인하면 저장. 개념 간 관계도 제안 → 승인 구조로 쌓아 마인드맵으로 전체를 정리

### 1-2. 책 스크랩 경로

- 처리 흐름 (10-12): 사진 → **OCR** → 추출 텍스트 → Claude 분석(텍스트 입력) → 태그 제안 + 근거 문장 → **서버가 근거 문장이 추출 텍스트 안에 글자 그대로 있는지 확인** → 승인 화면(사용자가 근거 문장 대조·수정) → 저장 (이미지·추출 전문은 폐기)
- OCR로 바꾼 이유
  - 원문 충실도: 전용 OCR은 글자 단위 오류라 눈에 띄지만, 언어모델은 틀릴 때 문장을 매끄럽게 지어내 티가 잘 안 남
  - 근거 문장을 OCR 텍스트와 글자 단위로 대조 가능
  - 요금: Claude 입력이 이미지 대신 텍스트라 줄 수 있으나 OCR 요금이 추가됨 → 어느 쪽이 싼지는 실측 필요
  - 사용자가 OCR 방식을 직접 경험해보고 싶어함 (학습 목적)
- 받아들이는 트레이드오프: 외부 서비스 1개 추가(계정/API 키/요금), 호출 단계 증가(실패 지점·대기 시간), 책 사진이 OCR 서비스로 전송됨 (이미지 저장은 하지 않음)
- 보관 정책
  - 원본 이미지: 저장하지 않음 → 이미지 스토리지(S3 등) 불필요
  - 추출 전문: 저장하지 않음. 분석과 근거 문장 검증에만 쓰고 폐기 (`BOOK_SCRAP`에 전문 필드 없음)
  - **근거 문장**: 저장함. "이 태그가 이 스크랩에 붙은 이유"에 속하는 정보이므로 `BOOK_SCRAP_TAG`에 `reason`과 함께 저장 (가칭 `excerpt`). 한 페이지에서 태그가 여러 개면 태그마다 다른 문장. 1~3문장 상한(수치는 구현 시 결정)
  - 뉴스(`ARTICLE`)는 본문이 대체로 길지 않아 기존대로 본문 저장
- 근거 문장 활용: 태그 상세의 "내 스크랩에서의 등장"에 reason과 함께 표시 / 관계 제안 시 책 쪽 근거 자료 / 원문 전체는 페이지 번호로 실물 책에서 찾음
- 페이지 번호: 사용자 수동 입력. 책 등록: 스크랩마다 개별 입력 (별도 `BOOK` 테이블 없음, **서재 기능도 도입하지 않음**)
- `BOOK_SCRAP`은 `ARTICLE`과 별도 테이블, `TAG`와의 연결도 `BOOK_SCRAP_TAG`로 별도
- 마인드맵/전체 피드는 두 테이블을 합쳐 조회 → 직접 SQL 또는 두 번 조회 후 서버 병합

### 1-3. 개념 간 관계(지식 그래프)

- 목적: 누적된 스크랩을 마인드맵으로 전체 정리
- 직접 관계를 저장 (`CONCEPT_RELATION`: `sourceTagId`, `targetTagId`, `reason`, `status` 등). 태그가 사용자별이므로 `userId`는 두지 않음
- 생성 주체: Claude가 제안, 사용자가 승인/수정/삭제
- 분류: 정형 카테고리 없이 자유 서술(`reason`)로 시작. 패턴이 쌓이면 역추출
- 방향성: 무방향 (인과/파생 뉘앙스는 `reason`으로만 표현)
- `status`: 제안 / 승인 / **거절** (10-12 추가). 거절한 관계는 삭제하지 않고 보존해 같은 쌍 재제안을 막음

**관계 판단 기준 (10-12): 스크랩 근거 필수**

| 방식 | 내용 | 결과 |
|---|---|---|
| A. 이론적 관계 | 학문적으로 연결되면 제안 | 배제 |
| B. 스크랩 근거 필수 | 사용자의 스크랩에서 두 개념이 함께 작동한 근거가 있어야 제안 | **채택** |
| C. 혼합 | 후보는 스크랩 근거, 의미 판단은 이론적 | 채택하지 않음 |

- A 배제 이유: 누구에게나 같은 교과서식 연결, 제안 수 폭증, 학설·학자 이름을 지어낼 위험과 검증 수단 부재
- B 채택 이유: "이 연결이 왜 내 마인드맵에 있는가"에 답할 수 있음, 원문 스크랩으로 근거 검증 가능, 10-10 태그 상세 방향과 일관, 09-17 결정(동시출현만으로는 관계로 보지 않음)과 충돌 없음
- 예: `감시사회`—`소외`는 한 뉴스 안의 근거로 제안. `판옵티콘`(책)—`감시사회`(뉴스)처럼 **서로 다른 스크랩에 걸친 근거도 허용**. 유명한 짝이어도 엮는 스크랩이 없으면(예: `아노미`—`소외`) 제안하지 않음
- 트레이드오프: 초기에는 연결이 적어 그래프가 빈약함
- 다른 스크랩끼리 허용하는 이유: 책(이론)과 뉴스(현실)의 연결은 대부분 서로 다른 스크랩에 걸쳐 생기며, 이것이 앱 정체성의 핵심
- 이로 인한 비용: API 입력 증가(→ 원문 대신 저장된 요약 + 연결 테이블 `reason`/`excerpt`만 전달), 스키마 복잡도(근거가 두 스크랩), 품질 관리, 운영 정책(삭제·재제안·검토 부담)
- 품질 관리 장치
  - 프롬프트: reason에 양쪽 스크랩의 구체적 내용을 각각 언급하도록 요구
  - 서버 검증: 인용된 스크랩이 해당 사용자 소유인지, 그 태그가 실제로 붙어 있는지 확인
  - 호출 1회당 제안 개수 상한 (수치는 구현 시 결정)

**마인드맵 단위 (10-12)**: 하나로 계속 누적. 월/주 단위 리셋·보관은 채택하지 않음 (책과 뉴스의 연결이 가장 먼저 끊기고, 분야별 분할과 같은 칸막이 문제이며, 잊은 개념을 다시 이어주는 역할을 사용자 검색에 떠넘김). "이 기간에 쌓인 것만 보기"는 월간 회고에서 `createdAt` 필터로 해결

### 1-4. 스크랩 저장 플로우

스크랩 입력(URL 또는 책 사진+페이지 번호) → [책: OCR] → Claude 분석 → 태그 제안(+책은 근거 문장) → 사용자 승인 → 스크랩·태그 저장 → 관계 제안 생성(백그라운드) → 홈/마인드맵에서 승인

- 승인 전 분석 결과는 앱(클라이언트)이 보관했다가 승인 시 한 번에 저장. 앱이 꺼지면 사라지는 한계를 감수 (책은 재촬영 필요). 불편해지면 서버 DB 임시 상태 저장으로 전환 검토
- 관계 제안은 태그 승인 직후 서버가 백그라운드 생성. 태그 저장은 즉시 완료

### 1-5. 태그 정책

- 소유: 처음부터 사용자별. `TAG`에 `userId` 추가, 이름 유일성은 "사용자 안에서 유일". 트레이드오프: 같은 개념이 사용자 수만큼 중복 저장, 사용자 간 공유 계획 없음
- 중복 방지
  - 태그 제안 시 해당 사용자의 기존 태그 목록을 Claude에 함께 전달
  - Claude는 태그마다 "기존 태그 ID" 또는 "새 태그 이름" 중 하나로 응답 → 서버는 ID로 연결, 새 태그 생성 횟수를 로그로 집계
  - 방어선 1: 승인 화면에서 새 태그 제안 시 "비슷한 기존 태그" 함께 표시
  - 방어선 2: 태그 병합 기능 (후순위)
  - 임베딩 자동 판별은 도입하지 않음 (부족하다고 실측된 뒤 재검토)

**결정된 필드 방향 (10-10, 10-12)**

## 5. 백엔드 API 설계 — 🔶 구 구조 기준 구현 완료, 수정 필요

**현재 구현 (구 구조 기준)**
- 인증: `POST /auth/signup`, `POST /auth/login` (JWT)
- 스크랩: `POST /articles`(URL → 크롤링 → Claude 분석 → 저장, 동기), `GET /articles`(페이지네이션 + publisher 필터), `GET /articles/:id`, `DELETE /articles/:id` — 본인 소유 확인 포함

**분석/저장 분리 (10-29 구현, 기사)**
- `POST /articles/analyze` `{ url }`: 중복 URL 확인(409 + `articleId`) → 크롤링 → Claude 분석 → 결과만 반환 (DB 저장 없음)
- `POST /articles`: analyze 결과 + 승인한 태그. 태그는 기존 `{ tagId, reason, explanation }` 또는 새 `{ name, category?, description?, reason, explanation? }`
  - 서버가 다시 검증: URL 형식(http/https), 필드 길이, 본문 100~5000자, 태그 1~10개, `tagId` 본인 소유, 같은 태그 중복
  - 기사·새 태그·ArticleTag를 한 트랜잭션으로 저장 (중간에 실패하면 아무것도 남지 않음)
  - 새 이름이 이미 내 태그에 있으면 그 태그를 씀 (사용자 안에서 이름 유일). Claude가 ID로 고르는 방식은 다음 단계
- 크롤러: `og:site_name` → `publisher`, 발행일을 못 찾으면 `null` (전에는 현재 시각으로 채움)
- 서버 테스트: `node:test` (`npm test`). 크롤러·Claude는 가짜로 바꾸고, 개발 DB에 임시 사용자를 만들었다 지움

**기존 태그 ID 재사용 (10-29 구현, 기사)**
- analyze가 사용자의 기존 태그 전체를 Claude에 넘김. 실제 UUID 대신 `T1`, `T2` … 번호로 보여 주고 서버가 번호 → 태그로 바꿈 (목록에 없는 번호는 버림 → 새 태그로 취급)
- 응답 태그: `{ tagId, name, isNew, category, description, reason, explanation, similarExisting: [{ id, name }] }`
  - 기존 태그면 `tagId`와 DB의 이름·설명 (사용자가 고친 설명 유지), 새 태그면 `tagId: null` + Claude가 고른 비슷한 기존 태그 최대 3개
  - 새 이름이 기존 태그와 글자까지 같으면 기존 태그로 보정하고 로그에 "이름 일치로 보정"으로 따로 셈. 같은 태그가 겹치면 하나만 남김
- 로그: `[태그 제안] 기존 태그 N개 중 재사용 a개, 새 태그 b개`, `[태그 저장] 새 태그 n개 생성`, `[Claude] 토큰 입력/출력` → 8번 실측(재사용 정확도·토큰)에 사용
- 응답 형식: 정규식 JSON 추출 → **구조화 출력**(`output_config.format` JSON 스키마). `stop_reason`이 `end_turn`이 아니거나 JSON이 깨지면 502, API 한도 초과는 503
- `Tag.category` 고정 목록 확정: 사회학, 철학, 정치학, 경제학, 심리학, 인류학, 커뮤니케이션학, 기타 (스키마 enum. 저장 요청에서 목록 밖 값은 "기타")
- `Article.summary`: og:description → **Claude가 쓴 2~3문장 요약** (관계 제안 입력용). 비면 og:description으로 대체
- 모델은 그대로 `claude-haiku-4-5-20251001`
- **분석 모델·태그 기준 변경 (11-01)**: 사용자 시험에서 학술 용어 대신 풀어 쓴 이름("불안과 지위 경쟁", "염세주의적 거리두기")이 나오고, 원문에 직접 나온 개념(염세주의)을 빼고 기존 태그만 다시 붙이는 문제
  - 원인: 기존 태그 재사용을 강하게 지시하면서 "원문에서 먼저 고르고 나중에 맞춰 본다"는 순서가 없었고, 조합형 이름 금지·원문 개념어 우선 규칙이 없었음 (개념은 요약이 아니라 원문 전체에서 뽑음)
  - 태그 기준: 원문만 보고 핵심 개념을 고른 뒤 기존 태그와 맞추기, 원문의 학술 용어 우선, "A와 B"·설명형 이름 금지(나쁜 예 → 바른 이름 짝), 용어가 정말 없을 때만 설명형 + reason에 밝힘. 채점 기준표도 같은 방향으로 감점 추가
  - 분석 모델 Haiku 4.5 → `claude-sonnet-5-5` (effort medium, `fallbacks: "default"`). 관계 제안은 Haiku 4.5 유지
  - 같은 샘플 비교 (책 1장, 기존 개념 4개를 넣고):
    - Haiku 4.5 + 이전 기준: 새 개념 0개, 기존 2개만 재사용. 약 10원, 9초
    - Opus 5.5 + 새 기준: "조건부 인정"·"무조건적 사랑" + 기존 1개. 약 89원, 22초 → 비용 때문에 제외
    - Sonnet 5.5 + 새 기준: "조건부 인정"·"무조건적 사랑". 약 29원, 10초 → 채택
- 남은 점: 태그가 수백 개로 늘면 매번 전체 목록을 보내는 비용이 커짐 → 실측 후 판단

**책 스크랩 (10-29 구현)**
- OCR 서비스: **Google Cloud Vision** `DOCUMENT_TEXT_DETECTION` + `languageHints: ['ko']`, REST 호출, 키는 `.env`의 `GOOGLE_VISION_API_KEY` (선정 이유: 월 1,000장 무료로 실측·MVP 감당, Node 연동 쉬움, 블록 위치 정보로 쪽번호 제거 가능)
- `POST /book-scraps/analyze` (multipart): `image`(JPEG/PNG/WebP, 7MB 이하, 긴 변 1000px 이상) + `bookTitle`, `author?`, `page?`
  - 사진은 multer 메모리 저장소로만 받고 디스크·DB에 남기지 않음. 형식·해상도는 파일 바이트로 확인 (확장자 `.jpg`인 WebP가 실제로 있었음)
  - 응답: `{ bookTitle, author, page, summary, ocrText, tags[] }`. 태그는 기사와 같은 형태 + `excerpt`, `excerptVerified`
  - `ocrText`는 승인 화면에서 근거 문장과 대조하라고 돌려줄 뿐 저장하지 않음
- `POST /book-scraps` (JSON): 책 정보 + `summary` + `tags[]`(각각 `excerpt` 필수, 300자 이하). `GET /book-scraps`(목록), `GET /book-scraps/:id`, `DELETE /book-scraps/:id`
- **근거 문장 검증**: 공백·줄바꿈을 모두 빼고 OCR 텍스트에 글자 그대로 들어 있는지 대조 (한국어 책은 단어 중간에서 줄이 바뀌어 공백으로는 판단 불가). 실패해도 버리지 않고 `excerptVerified: false`("확인 필요")로 넘겨 승인 화면에서 실물 책과 대조·수정. 저장 시에는 OCR 텍스트가 없으므로 길이만 확인
- **OCR 결과 정리**: Vision의 글자 끊김 정보로 공백·줄바꿈을 복원하고, 페이지 위·아래 12% 안의 숫자만 있는 블록은 쪽번호로 보고 제거. 머리말·앱 표시 등 나머지 잡음은 규칙으로 거르지 않고 Claude 프롬프트에서 무시하게 함 (근거 문장 검증이 지어낸 문장을 막음)
- 실측 (10-29, 독서 앱 인증 이미지 1장, 960×1280): 본문 인식은 흐림·기울기·형광펜에도 거의 정확. 앱이 덧붙인 글자(날짜·책 정보 카드·독서 시간)가 본문 줄 사이에 섞이고, 본문을 덮은 부분은 깨짐. 표지 미리보기(약 260px)는 큰 제목만 인식 → 최소 해상도 기준의 근거
- 기사·책 공용 코드: `tagService`(기존 태그 조회·제안 정리·저장 시 태그 확정), `utils/validate`(입력 검증)
- **근거 문장 구간화 (10-29)**: 실측에서 Claude가 떨어진 문장을 이어 붙여(접속사 생략 포함) 2개 모두 검증 실패 → Claude는 원문에서 이어진 구간 1~3개(`excerpts`)를 주고, 서버가 구간마다 대조한 뒤 ` … `로 이어 `excerpt` 하나로 저장. 같은 실측에서 태그 이름이 설명문("사회적 지위의 조건부 인정")으로 나와 공통 태그 기준에 "짧은 개념어" 규칙과 예시 추가 → "조건부 인정", "상대적 박탈감"으로 개선
- 다시 돌린 실측에서는 오버레이에 가려진 본문을 Claude가 "예를 들어, … 돈이나"처럼 지어냈고, 검증이 "확인 필요"로 잡음 (의도대로 동작)
- **책 스크랩 제목 (10-29 결정)**: `BOOK_SCRAP`에 제목 필드를 추가하지 않고, 클라이언트가 제목 자리에 `summary`를 보여 준다 (서버 연동 시 클라이언트 `Scrap.title`/`ScrapAnalysis.title`을 책은 요약으로 채움)

**관계·마인드맵 (10-29 구현)**
- `GET /concepts/graph` (전체: 개념 + 거절 아닌 관계), `?center=<id>` (중심 개념 + 직접 연결), `GET /concepts/graph/preview?limit=15` (최근 추가 절반 + 연결 많은 개념)
- `GET /concepts` (스크랩 수·승인 연결 수·제안 수), `GET /concepts/:id` (설명 → 스크랩에서의 등장(reason·excerpt) → 연결(승인 먼저) → 처음 등장일), `PATCH /concepts/:id` (설명 수정 → `descriptionByAi: false`), `DELETE /concepts/:id`, `POST /concepts/:id/merge { intoId }`
  - 병합: 스크랩 연결 이동(같은 스크랩에 둘 다 있으면 하나만), 관계 이동(겹치면 하나로, 상태는 승인 > 거절 > 제안, 근거 합침), 둘 사이 관계 삭제
- `GET /relations?status=`, `GET /relations/:id` (근거 스크랩 포함, 책은 제목 자리에 요약), `PATCH /relations/:id { status?, reason? }`
  - **연결 끊기도 REJECTED로 보존** (10-29 결정, 재제안 방지). 앱의 되돌리기는 이전 상태로 PATCH
- 스크랩 삭제 시 근거가 0개가 된 관계(거절 제외)를 같은 트랜잭션에서 삭제 (`articleService.deleteArticle`, `bookScrapService.deleteBookScrap`)
- **관계 제안 2단계** (10-29, `relationSuggestService.js`): 스크랩 저장 응답 뒤 서버 프로세스 안에서 실행
  1. 후보: 개념 이름 목록(새 스크랩 개념 ★, 이미 있는 쌍은 제외 목록)만 보고 후보 쌍 최대 8개
  2. 근거 확인: 새 스크랩 + 상대 개념이 붙은 최근 스크랩(개념마다 3개)의 요약·태그 이유·근거 문장으로 확인, 최대 3개 제안
  3. 서버 검증: 후보에 있던 쌍인지, 근거 스크랩이 내 것이고 두 개념이 각각 붙어 있는지 → SUGGESTED로 저장
  - 실측 (10-29, 임시 데이터): 판옵티콘(책)—감시사회(기사), 감시사회—소외(같은 기사) 제안, 근거 없는 아노미—소외 등은 걸러짐. 호출 1회(2단계 합계) 약 8원
  - 첫 실측에서 Claude가 번호 대신 개념 이름("감시사회 ★", 오타 "판옥티콘")으로 답해 후보가 전부 버려짐 → **번호 필드를 JSON 스키마 enum으로 묶음** (태그 재사용 `existingTag`에도 같은 위험이 있어 함께 적용). 이유 문장에 S1 같은 내부 번호가 섞여 프롬프트로 금지
  - 비용 기록: `server/logs/relations-YYYY-MM.jsonl` (단계별 토큰·비용, 후보 수, 제안 수). `RELATION_SUGGEST=off`면 끔 (테스트)
  - 아직 없음: 이미 있는 관계에 새 근거 스크랩 추가, 관계 제안 품질 채점

**신규 흐름에 따른 변경 (엔드포인트 구성은 가칭)**
- 분석과 저장의 분리: "분석해서 결과만 반환"(저장 없음)과 "승인된 태그와 함께 저장". 저장 요청에 클라이언트 보관 분석 결과가 실려 오므로 서버가 태그 ID 소유권, 입력 길이, **책의 경우 근거 문장 검증 결과** 등을 확인
- 책 스크랩 경로: 이미지 + 사용자 입력(책 제목, 페이지 등)을 받는 분석 엔드포인트 신설 (이미지 업로드 처리, OCR 호출, OCR 결과 정리: 줄바꿈·머리말·쪽번호 등 본문 외 텍스트 처리)
- 마인드맵: **중심 노드 기준 조회**(태그 하나 + 직접 연결된 개념, ARTICLE/BOOK_SCRAP UNION 포함), 홈 미리보기용 태그 조회(최근 추가 + 연결 많은 태그 10~20개, 관계 상태 포함)
- 관리: 관계 승인/거절/수정/삭제, 태그 병합·삭제는 목록 기반 화면용 API
- 태그: 목록, 태그 상세(설명, 내 스크랩에서의 등장 + reason/excerpt, 연결된 개념), 검색/자동완성 ("비슷한 기존 태그" 표시에도 활용)
- 인증 보완: 토큰 갱신(refresh), 로그아웃
- URL 중복 스크랩 방지

**동기/비동기 처리**
- 분석 단계는 MVP 동기 처리 유지
- 관계 제안은 태그 승인 후 백그라운드 생성. 작업 큐까지 갈지, Express 프로세스 안에서 응답 후 이어서 실행할지 결정 필요 (제안은 다시 만들 수 있는 데이터라 MVP에서는 유실 감수 가능)

| 방식                    | 장점                        | 단점                                       |
| ----------------------- | --------------------------- | ------------------------------------------ |
| 프로세스 내 후속 실행   | 구현 단순, 추가 인프라 없음 | 재시작 시 유실, 실패 재시도 직접 구현 필요 |
| 작업 큐 (Bull/Redis 등) | 재시도/상태 관리 용이       | Redis 추가, 복잡도 증가                    |

**그 외**: 에러 응답 포맷 통일(크롤링/OCR/분석 실패 안내), URL 형식 및 접근 가능 여부 사전 체크

- **태그 제안**: 기존 태그 목록을 함께 전달하고 태그마다 "기존 ID" 또는 "새 이름"으로 응답. `Tag.name` 완전 일치 재사용 코드는 제거 대상

  - **비용 통제 (우선 검토: 2단계 방식)**: 1단계(저렴) 새 태그를 기존 태그 이름 목록 전체와 비교해 연결 후보만 선정 → 2단계(상세) 후보 쌍에 한해 해당 스크랩의 요약·reason을 보내 근거 확인 후 제안
    - 장점: 오래된 책 스크랩도 후보에 오를 수 있고 비싼 근거 확인은 소수에만 수행 / 단점: 호출 2회, 구현 복잡도 증가
    - 대안: 근거 상세 전달을 최근 기간 스크랩으로 제한 (단순하지만 오래된 스크랩과의 연결이 약해짐)
    - 확정은 실측(호출당 토큰 기록) 후
- **개념 설명 생성**: AI 생성 표시, 사용자 수정 가능 전제
- 응답 포맷: 정규식 추출 → tool use(structured output) 전환 권장 (ID/이름 구분, 근거 문장 등 구조가 중요해짐)
- 실패/재시도, rate limit 초과 처리 로직 추가

- ✅ ③ 기사 스크랩 (10-31)
  - `ApiScrapAnalysisRepository`(`POST /articles/analyze`), `ApiScrapRepository`(최근 스크랩 = `GET /articles` + `GET /book-scraps`를 합쳐 최근순, 저장 `POST /articles`·`/book-scraps`)

  - 분석·저장 실패는 서버 문구를 그대로 보여 준다 (이미 스크랩한 기사, 분석 횟수 초과 등). 저장 뒤 그래프·최근 스크랩 Provider를 갱신
  - 기사 출처 줄의 날짜는 발행일(`publishedAt`), 없으면 저장한 날
  - 실제 서버로 확인 (클라이언트 Api 저장소 코드로, 화면은 거치지 않음): 경향신문 기사 분석 → 태그 2개 승인·저장 → 최근 스크랩, 같은 기사 재분석 시 "이미 스크랩한 기사입니다."
- ✅ ④ 책 스크랩 (10-31)
  - 사진: `image_picker`로 카메라 촬영·앨범 고르기 (`PagePhotoSource`, 웹은 둘 다 파일 고르기). 웹에서도 쓰도록 경로 대신 바이트(`PagePhoto.bytes`)를 들고, 긴 변 2400px·품질 85로 줄여 보낸다 (서버: 긴 변 1000px 이상, 7MB 이하). 취소하면 이전 사진 유지, 권한 거부는 안내 문구. iOS `Info.plist`에 카메라·사진 권한 문구 추가
  - 분석: `POST /book-scraps/analyze` multipart (`image`, `bookTitle`, `author?`, `page?`). 요약이 제목, 출처 줄은 "책 · 저자 · 쪽"
  - 태그 승인: 근거 문장을 따옴표로 보여 주고, 서버 검증에 실패한 문장(`excerptVerified: false`)에 "확인 필요" 배지 + 안내. "근거 문장 수정하기"로 고치면 배지가 사라지고 고친 문장으로 저장 (OCR 전문은 돌려보내지 않음)
  - 토큰 만료로 다시 보낼 때 FormData는 재사용할 수 없어 `AuthInterceptor`가 복제해서 보낸다
  - 실제 서버로 확인 (클라이언트 Api 저장소 코드로, 화면은 거치지 않음): 샘플 사진 → OCR·분석(근거 문장 "확인 필요" 1건, 앱 표시 잡음 때문) → 저장 → 최근 스크랩. 웹 릴리스 빌드 통과
  - 남은 점: 실제 기기 카메라·웹 파일 고르기 화면은 직접 눌러 보지 않음. 분석 대기 중 단계 표시(OCR → 분석)는 넣지 않음. 근거 문장 300자 제한은 서버 문구로만 안내
- 마인드맵 점선 탭 → 승인/거절
- 공유하기 메뉴로 URL 받기(이후)
- 확인 필요: 기본 병렬 `flutter test`가 중간에 멈추는 문제
- 태그 병합은 8-6에서 "이후"로 분류했지만 Figma 관리 화면에 포함돼 있어 클라이언트에는 먼저 구현됨 (서버 API는 미구현)

### 8-1. 홈
- 구성: 상단 떠다니는 태그 영역 + 하단 스크랩 피드(뉴스+책 통합) + 스크랩 추가 버튼
- 떠다니는 태그: 전체가 아닌 **최근 추가 + 연결 많은 태그 10~20개**. 탭하면 태그 상세로 이동. 승인된 관계는 옅은 실선, 제안은 점선 → 마인드맵 미리보기
- **관계 제안 발견 문제**: 별도 제안함/알림 뱃지는 쓰지 않는 결정(09-30) 유지. 대신 홈 태그 사이에 점선이 나타나 새 제안을 자연스럽게 발견하게 함
- 신규 사용자(태그 0~3개): 빈 상태를 "스크랩할수록 채워지는 공간"이라는 성장 연출로 활용
- 피드: 뉴스/책을 아이콘·출처로 구분, 항목마다 태그 표시
- 홈은 가장 자주 열리므로 애니메이션은 은은하게 (성능 우선)

### 8-2. 마인드맵
- 분야/키워드/기간별 분할은 하지 않음 (분야를 넘나드는 연결이 핵심 가치이기 때문)
- **기본 방식: 중심 노드 탐색** — 태그 하나를 가운데 두고 직접 연결된 개념만 주변에 표시, 주변 태그를 누르면 새 중심. 한 화면 10개 안팎이라 세로 화면에 적합하고 태그 증가에 강함. 시작점은 홈의 태그 탭 또는 검색
- 전체 그래프는 노드 100개 전후부터 실용성이 떨어져 기본 화면으로 쓰지 않음
- **탐색과 관리 분리**: 그래프는 둘러보기용, 관리(태그 병합·삭제, 관계 승인/거절/수정)는 일반 목록 화면 (그래프 위 터치 조작은 부정확·실수 위험)
- 승인 = 실선, 제안 = 점선, 점선을 눌러 승인/거절 (그래프 안 표시 결정 유지)
- 나중에 묶음이 필요하면 미리 정한 분야가 아니라 데이터에서 생긴 덩어리(촘촘히 이어진 태그 무리)를 보여주는 방식
- **결정 (10-28)**: Flutter 그래프는 라이브러리 없이 직접 캔버스(`CustomPainter` + 방사형 배치)로 구현함. 중심 노드 기준 10개 안팎이라 충분
- **배치 연속성 (11-01)**: 중심을 바꿀 때마다 배치를 처음부터 계산해(우선순위 순서, 항상 왼쪽 위에서 시작) 같은 개념이 매번 다른 자리로 가고, 연결 1개면 세로 한 줄이 되는 문제 → 직전 배치를 넘겨 새 중심에서 본 예전 방향 순서대로 놓고, 직전 중심은 눌러 들어온 반대쪽에 둠. 1단계가 1~2개면 좌우 배치. 데이터 갱신으로 다시 그려도 배치 유지 (`radialLayout`의 `previous`)

### 8-3. 태그 상세
- 표시 순서: ① 개념 설명(짧게, AI 생성 표시 + 수정 가능) → ② **내 스크랩에서의 등장**(어떤 기사/책에서 왜 붙었는지 reason, 책은 근거 문장 excerpt 함께, 뉴스/책 구분) → ③ 연결된 개념(관계 reason 포함) → ④ 처음 등장한 날짜 등
- 핵심은 ②: 일반 정의는 사전으로도 얻지만 "내가 읽은 글에서 이렇게 쓰였다"는 이 앱에서만 볼 수 있는 정보

### 8-4. 스크랩 추가 / 태그 승인 화면
- 스크랩 추가: URL 입력 / 책 사진 촬영 + 페이지 번호 입력, 분석 진행 상태 (책은 OCR 단계가 추가되어 대기 시간이 길어질 수 있음 → 단계 표시 고려)
- 태그 승인: 제안 태그 확인·수정·거절, 새 태그일 때 비슷한 기존 태그 표시, **책은 근거 문장을 보여주고 사용자가 수정 가능** (승인 시점에 실물 책이 손에 있으므로 OCR 오류를 그 자리에서 대조)
- 화면 이탈 시 확인 안내 정도만 고려 (승인 전 유실은 감수)

### 8-5. 통계 (MVP 제외, 최하위 우선순위)
- 단순 수치(태그 개수, 분야 분포)는 재방문 이유가 약함
- 만든다면: **책과 뉴스에 모두 등장한 개념**, 연결이 가장 많은 개념, 아무것과도 연결되지 않은 개념. 별도 탭보다 **월간 회고** 형태 검토 (`createdAt` 필터 활용)

### 8-6. MVP 범위
- **MVP**: 홈(떠다니는 태그 + 피드 + 추가), 스크랩 추가·태그 승인, 태그 상세, 마인드맵(중심 노드 탐색), 관계/태그 관리 목록
- **이후**: 통계/월간 회고, 휴대폰 "공유하기" 메뉴에서 URL 바로 보내기 (뉴스 입력 편의에 큰 영향), 태그 병합

### 8-7. 기술/UX
- 상태관리(Riverpod): 인증, 스크랩 목록/상세, 태그 목록/필터, 승인 대기 중인 분석 결과(클라이언트 보관분), 마인드맵 데이터(중심 노드 기준)
- 분석 대기 로딩 경험(스켈레톤/애니메이션), dio interceptor로 JWT 자동 첨부 및 갱신, go_router 인증 가드
- 디자인 진행 순서: FigJam 화면 흐름도 → 작은 디자인 시스템 → 태그 승인·마인드맵·태그 상세·홈 시안

## 9. 인증/보안 — ✅ 서버 보완 완료 (10-29)

**구현 완료**: bcrypt 해싱(`SALT_ROUNDS = 10`), JWT 발급/검증(Bearer), 로그인 실패 시 이메일 존재 여부 비노출

**보완 (10-29)**
- **Access/Refresh 토큰 분리**: Access JWT 15분(HS256 고정 검증), Refresh는 임의 문자열 30일
  - `REFRESH_TOKEN` 테이블 추가 (10-29 결정, **테이블 9개**): 토큰 해시만 저장, `familyId`(한 번의 로그인)로 기기별 로그아웃
  - 갱신할 때마다 새 토큰으로 교체, 이미 교체된 토큰이 다시 오면 탈취로 보고 그 로그인의 토큰을 모두 폐기
  - API: `POST /auth/login` → `{ accessToken, refreshToken, user }`, `POST /auth/refresh { refreshToken }`, `POST /auth/logout { refreshToken }`
- **Rate limiting** (`express-rate-limit`, 메모리 저장): 분석(기사+책 합산) 사용자별 **시간당 20회·하루 60회** (10-29 결정, 사용자당 하루 최대 약 1,500원), 실패 응답은 세지 않음. 로그인 IP별 실패 10회/15분, 토큰 갱신 30회/15분
  - 서버를 여러 대로 늘리면 Redis 등 공용 저장소로 바꿔야 함. 관계 제안은 저장 1건당 1회라 분석 상한으로 함께 묶임
- **CORS**: `CORS_ORIGINS`(쉼표 구분)에 넣은 출처만 허용, 없으면 다른 출처 불허 (모바일 앱은 해당 없음, 웹 빌드 배포 시 설정)
- **입력 검증**: 회원가입 이메일 형식(소문자로 저장)·비밀번호 8~72바이트(bcrypt 한도)·닉네임 30자, JSON 본문 100kb 상한, 깨진 JSON 400. 저장 요청의 태그 ID 소유권·길이·근거 문장 길이 검증은 1~3단계에서 완료
- 500 오류는 메시지를 숨기고 로그에만 남김 (DB 오류 등 내부 정보 노출 방지). 서비스가 일부러 만든 502·503 안내는 그대로
- `helmet` 보안 헤더, `JWT_SECRET`이 없으면 서버가 시작하지 않음
- 배포 시: 프록시 뒤라면 `TRUST_PROXY`(예: 1)를 줘야 IP별 제한이 실제 클라이언트 IP로 동작

**남은 것**
- 프론트 토큰 저장은 `flutter_secure_storage`, dio interceptor로 401이면 `/auth/refresh` 후 재시도 (프론트 연동 때)
- XSS: 서버는 JSON만 돌려주고 Flutter는 텍스트로 그리므로 현재 해당 없음. 웹뷰로 HTML을 그리게 되면 다시 검토
- **개인정보 측면 (10-12)**: 책 사진이 외부 OCR 서비스로 전송되므로 서비스 선정 시 데이터 보관·학습 사용 정책 확인 (앱 쪽은 이미지를 저장하지 않음)
- 근거 문장은 1~3문장의 짧은 인용 수준으로 제한 (저장량·저작권 부담 최소화)
