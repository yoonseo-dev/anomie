# Anomie 프로젝트 계획

> 뉴스 URL 또는 책 사진을 스크랩하면 Claude AI가 사회학/철학 개념을 분석해 태그로 연결하고, 개념 간 관계를 마인드맵(지식 그래프)으로 정리해주는 모바일 스크랩북 앱
> Flutter(모바일) + Node.js(백엔드)

최초 작성: 2026-09-17 / 최종 갱신: 2026-09-30 (기획 변경사항 반영)

## 1. 기획 단계 — ✅ 완료

- 서비스명: Anomie / 플랫폼: Flutter(모바일) + Node.js(백엔드)
- 핵심 컨셉(09-30 기준): 뉴스 URL 또는 책 사진을 스크랩하면 Claude가 개념 태그를 제안하고, 사용자가 승인하면 저장. 개념 간 관계도 제안 → 승인 구조로 쌓아 마인드맵으로 전체를 정리

### 1-1. 기획 변경 요약 (09-17 → 09-30)

| 항목            | 기존                          | 변경 후                                              |
| --------------- | ----------------------------- | ---------------------------------------------------- |
| 입력 방식       | 뉴스 URL                      | URL + 책 사진 촬영 병행                              |
| 처리 파이프라인 | URL → 크롤링 → Claude 분석    | 책 경로 신설: 사진 → Claude Vision. URL 경로는 유지  |
| 태그 간 관계    | 없음                          | 개념끼리 직접 관계를 갖는 지식 그래프                |
| 스크랩 테이블   | `ARTICLE` 단일                | `ARTICLE`(뉴스) + `BOOK_SCRAP`(책) 분리              |
| 태그 저장       | 분석 결과 그대로 저장         | Claude가 제안 → 사용자 승인 후 저장                  |
| 태그 소유       | 전역                          | 사용자별                                             |

### 1-2. 책 스크랩 경로

- 텍스트 추출: Claude Vision에 이미지를 직접 넣어 "텍스트 추출 + 개념 분석"을 한 번에 처리 (별도 OCR 미사용)
- 원본 이미지: 저장하지 않고 정보 정리 직후 폐기 → 이미지 스토리지(S3 등) 불필요
- 페이지 번호: 사용자 수동 입력
- 책 등록: 스크랩마다 개별 입력 (별도 `BOOK` 테이블 없음)
- `BOOK_SCRAP`은 `ARTICLE`과 별도 테이블. `TAG`와의 연결도 `BOOK_SCRAP_TAG`로 별도
- 마인드맵/전체 피드는 두 테이블을 합쳐 조회해야 함 → Prisma 기본 문법으로 어려우므로 직접 SQL 또는 두 번 조회 후 서버 병합

### 1-3. 개념 간 관계(지식 그래프)

- 목적: 누적된 스크랩을 마인드맵으로 전체 정리
- 개념과 개념 사이의 직접 관계를 저장 (`CONCEPT_RELATION`: `sourceTagId`, `targetTagId`, `reason`, `status`(제안/승인) 등)
- 태그가 사용자별이므로 `CONCEPT_RELATION`에는 `userId`를 두지 않음
- 생성 주체: Claude가 제안, 사용자가 승인/수정/삭제
- 분류: 정형 카테고리 없이 자유 서술(`reason`)로 시작. 패턴이 쌓이면 카테고리를 역추출
- 방향성: 무방향 (인과/파생 뉘앙스는 `reason` 텍스트로만 표현)
- UI/UX: 마인드맵 안에 함께 표시. 승인 = 실선, 제안 = 점선, 점선을 눌러 승인/거절. 별도 제안함/알림 뱃지는 사용하지 않음

### 1-4. 스크랩 저장 플로우

스크랩 입력 → Claude 분석 → 태그 제안 → 사용자 승인 → 스크랩·태그 저장 → 관계 제안 생성(백그라운드) → 마인드맵에서 승인

- 승인 전 분석 결과는 앱(클라이언트)이 보관했다가 승인 시 한 번에 저장. 승인 전 앱이 꺼지면 결과가 사라지는 한계를 감수 (책은 재촬영 필요). 불편해지면 서버 DB 임시 상태 저장으로 전환 검토
- 관계 제안은 태그 승인 직후 서버가 백그라운드로 생성. 태그 저장은 즉시 완료되고 사용자는 Claude 호출을 연속으로 기다리지 않음

### 1-5. 태그 정책

- 소유: 처음부터 사용자별 (전역 후 전환은 데이터 축적 뒤 어렵고, 태그 수정이 타 사용자에 영향을 주는 문제로 배제)
  - `TAG`에 `userId` 추가, 이름 유일성은 "사용자 안에서 유일"
  - 트레이드오프: 같은 개념이 사용자 수만큼 중복 저장, 사용자 간 공유 기능은 현재 계획 없음
- 중복 방지:
  - 태그 제안 시 해당 사용자의 기존 태그 목록을 Claude에 함께 전달
  - Claude는 태그마다 "기존 태그 ID" 또는 "새 태그 이름" 중 하나로 응답 → 서버는 문자열 비교 없이 ID로 연결, 새 태그 생성 횟수를 로그로 집계
  - 방어선 1: 승인 화면에서 새 태그 제안 시 "비슷한 기존 태그"를 함께 표시
  - 방어선 2: 태그 병합 기능 (후순위)
  - 임베딩 유사도 자동 판별은 도입하지 않음 (방어선이 부족하다고 실측된 뒤 재검토)
- 검증: 서버 구현 후 실제 기사 10~20개로 태그 재사용 정확도 측정

## 3. 데이터베이스 설계 — 🔶 재설계 필요

**확정된 테이블 (7개)**: `USER`, `TAG`(userId 추가), `ARTICLE`, `BOOK_SCRAP`, `ARTICLE_TAG`, `BOOK_SCRAP_TAG`, `CONCEPT_RELATION`

**현재 상태 (구 구조 기준 구현)**
- `User` — `Article` — `Tag`(`ArticleTag` 경유 다대다) 구조의 `schema.prisma` 작성 및 마이그레이션 6개 적용 (`init` → `add_tag_category` → `add_article_publisher` → `add_articletag_explanation` → `add_commentary` → `add_article_analysis_fields`)
- `Article`에 분석 필드(`publisher`, `commentary`, `framing`, `rhetoric`, `stakeholders`, `values`), `ArticleTag`에 `reason`/`explanation`, `Tag`에 `category`/`description`이 이미 있음

**진행 방침**
- `schema.prisma`를 7개 테이블 구조로 재작성. 개발 DB에 실제 데이터가 없으므로 초기화 후 새로 적용해도 손실 없음 (기존 마이그레이션 6개는 폐기하고 새로 생성)
- 필드 설계 초안을 제시하고 검토하는 방식으로 진행

**필드 설계 시 결정할 점**
- 기존 분석 필드(`framing`, `rhetoric` 등)는 뉴스 특화 성격이 강함 → `BOOK_SCRAP`에 어떤 필드를 둘지 (책 제목, 저자, 페이지, 추출 텍스트 등), 공통 필드를 어디까지 맞출지
- `Tag.category`를 유지할지
- 연결 테이블(`ARTICLE_TAG`, `BOOK_SCRAP_TAG`)의 `reason`/`explanation` 유지 여부
- `CONCEPT_RELATION`의 같은 쌍 중복(A—B와 B—A) 방지 방식 (무방향이므로 저장 규칙 필요)

**후속 작업**
- 기존 ERD(`anomie_erd.html`)는 구 구조이므로 필드 확정 후 갱신
- 새 마이그레이션 폴더 등 untracked 파일은 스키마 재작성 전에 한 번 커밋해 구 구조를 보존

## 5. 백엔드 API 설계 — 🔶 구 구조 기준 구현 완료, 수정 필요

**현재 구현 (구 구조 기준)**
- 인증: `POST /auth/signup`, `POST /auth/login` (JWT 발급)
- 스크랩: `POST /articles`(URL → 크롤링 → Claude 분석 → 저장, 동기), `GET /articles`(페이지네이션 + publisher 필터), `GET /articles/:id`, `DELETE /articles/:id` — 본인 소유 확인 포함

**신규 흐름에 따른 변경 (엔드포인트 구성은 가칭)**
- 분석과 저장의 분리: "분석해서 결과만 반환"(저장 없음)과 "승인된 태그와 함께 저장"으로 나눠야 함. 현재의 "분석 후 즉시 저장" 구조와 크게 달라지는 부분
  - 저장 요청에는 클라이언트가 보관한 분석 결과가 실려 오므로, 서버는 태그 ID가 본인 소유인지 등을 검증해야 함
- 책 스크랩 경로: 이미지 + 사용자 입력(책 제목, 페이지 등)을 받는 분석 엔드포인트 신설. 이미지 업로드 처리 필요
- 마인드맵: 사용자의 태그 + 관계 전체 조회 (ARTICLE/BOOK_SCRAP UNION 포함), 관계 승인/거절/수정/삭제
- 태그: 목록, 태그별 스크랩 조회, 검색/자동완성 (승인 화면의 "비슷한 기존 태그" 표시에도 활용 가능)
- 인증 보완: 토큰 갱신(refresh), 로그아웃
- URL 중복 스크랩 방지

**동기/비동기 처리 (결정 갱신 필요)**
- 기존 결정: MVP는 동기 처리 (분석까지 한 번에). 이 결정은 "분석" 단계에 그대로 유효
- 신규 발생: 관계 제안은 태그 승인 후 백그라운드 생성. 작업 큐(Bull/Redis)까지 갈지, Express 프로세스 안에서 응답 후 이어서 실행할지 결정 필요. 후자는 구현이 단순하지만 서버 재시작 시 작업이 유실될 수 있음 (제안은 다시 만들 수 있는 데이터라 MVP에서는 감수 가능한 수준)

| 방식                          | 장점                       | 단점                                       |
| ----------------------------- | -------------------------- | ------------------------------------------ |
| 프로세스 내 후속 실행         | 구현 단순, 추가 인프라 없음 | 재시작 시 유실, 실패 재시도 직접 구현 필요 |
| 작업 큐 (Bull/Redis 등)       | 재시도/상태 관리 용이      | Redis 추가, 복잡도 증가                    |

**그 외**
- 에러 응답 포맷 통일 (크롤링 실패/분석 실패 안내)
- URL 형식 및 접근 가능 여부 사전 체크

## 6. 크롤링 모듈 설계 — 🔶 부분 구현

**구현 완료** (`src/services/crawlerService.js`)
- Cheerio 기반: `fetch` + `cheerio.load`
- 추출 3단계: OG 메타태그 → 본문 셀렉터 목록(국내 뉴스 다수 커버) → 50자 이상 `<p>` 수집 폴백
- `article:published_time` → 발행일 파싱

**미구현 / 미결정**
- Puppeteer 폴백 (의존성만 있고 코드 미사용). 현재는 Cheerio 실패 시(본문 100자 미만) 400 에러
- robots.txt 정책
- 페이월 기사 처리 (제목/썸네일만 저장하는 방안)
- 본문 5000자 초과 시 무조건 거부 (`articles.js`) — 요약 후 분석 등 대안 미구현

**Cheerio vs Puppeteer**

|                  | Cheerio        | Puppeteer                |
| ---------------- | -------------- | ------------------------ |
| 방식             | 정적 HTML 파싱 | 헤드리스 브라우저 렌더링 |
| 속도/자원        | 빠르고 가벼움  | 느리고 무거움            |
| JS 렌더링 사이트 | 불가           | 가능                     |

- 방침: Cheerio 우선, 실패 시에만 Puppeteer 폴백 (하이브리드). 폴백 구현 시점은 실제 실패 사례를 보고 결정해도 무방
- 참고: 책 스크랩 경로는 크롤링을 거치지 않으므로 이 모듈과 무관

- 모델 `claude-haiku-4-5-20251001`, `messages.stream` + `finalMessage()`
- 태그명 자유 생성 + 시스템 프롬프트 기준(학문적 근거, 변별력, 최대 3개)
- `ArticleTag.reason`/`explanation` 및 기사 전체 분석 필드 생성
- 본문 5000자 초과 시 거부로 비용 관리
- 응답을 텍스트에서 정규식(`/\{[\s\S]*\}/`)으로 JSON 추출 → Claude가 JSON 앞뒤에 텍스트를 섞으면 깨질 위험

**신규/변경 요구사항**
- 태그 제안: 사용자의 기존 태그 목록을 함께 전달하고, 태그마다 "기존 ID" 또는 "새 이름"으로 응답하게 프롬프트 재설계. 기존의 "유사 태그 병합 로직 추가" 계획은 이 방식과 승인 화면의 유사 태그 표시로 대체됨 (`Tag.name` 완전 일치 재사용 코드는 제거 대상)
- 책 경로: 이미지를 직접 입력해 텍스트 추출 + 개념 분석을 한 번에 수행. 이미지 크기/개수 제한, 토큰 비용 확인 필요
- 관계 제안: 새로 승인된 태그와 기존 태그들 사이의 관계 후보를 생성하는 별도 호출 신설 (백그라운드). 입력에 넣을 태그 범위(전체 vs 최근/관련 태그)는 비용과 직결되므로 구현 시 결정
- 응답 포맷: 정규식 추출 → tool use(structured output)로 전환 권장. 태그 ID/이름 구분 응답처럼 구조가 중요해지므로 필요성이 커짐
- 실패/재시도, rate limit 초과 처리 로직 추가

**태그 생성 방식 (결정 기록)**
- 초기 검토안은 A(고정 택소노미) → B/C 확장이었으나, 실제 구현과 09-30 결정은 "사용자별 자유 생성 + 기존 태그 재사용(ID 지정)". 태그 품질은 재사용 정확도 측정(10~20개 기사)으로 검증하고, 미달 시 태그 병합 기능/임베딩을 재검토

## 8. 프론트엔드 설계 — ⬜ 미착수

**화면 (초안, 신규 반영)**
- 로그인/회원가입
- 홈: 스크랩 피드 (뉴스 + 책 통합), 태그 필터
- 스크랩 추가: URL 입력 / 책 사진 촬영 + 페이지 번호 입력, 분석 진행 상태
- **태그 승인 화면 (신규)**: 제안 태그 확인·수정·거절, 새 태그일 때 비슷한 기존 태그 표시
- 스크랩 상세: 요약/추출 텍스트 + 태그 + reason
- **마인드맵 (신규)**: 태그·관계 그래프, 실선(승인)/점선(제안), 점선 탭 시 승인/거절
- 태그 탐색, 마이페이지

**상태관리(Riverpod)**: 인증, 스크랩 목록/상세, 태그 목록/필터, 승인 대기 중인 분석 결과(클라이언트 보관분), 마인드맵 데이터

**미결정 (신규)**
- 마인드맵 그래프를 그릴 방법: Flutter용 그래프 라이브러리 사용 vs 직접 캔버스 구현. 노드 수가 늘면 성능/조작성(확대·이동·탭)이 관건이라 프론트 착수 전 후보를 비교해볼 필요가 있음
- 승인 전 앱 종료 시 유실을 어느 정도까지 허용할지는 09-30에 감수하기로 했으므로, 화면 이탈 시 확인 안내 정도만 고려

**UX**
- 분석 대기 로딩 경험 (스켈레톤/애니메이션)
- dio interceptor로 JWT 자동 첨부 및 만료 시 갱신
- go_router 인증 가드

## 9. 인증/보안 — 🔶 기본 구현 완료

**구현 완료**
- bcrypt 해싱 (`SALT_ROUNDS = 10`)
- JWT 발급/검증 (`authMiddleware`, Bearer 헤더)
- 로그인 실패 시 이메일 존재 여부 비노출

**보완 필요**
- Access/Refresh 토큰 분리 (현재 Access 하나, 만료 7일. Access는 짧게, Refresh는 길게)
- 토큰 저장: 프론트에서 `flutter_secure_storage` 사용 (SharedPreferences는 평문)
- CORS 설정 (배포 시 프론트 도메인 명시)
- **Rate limiting**: Claude 호출 엔드포인트는 비용 직결. 신규 구조에서는 분석 엔드포인트(URL/이미지)와 관계 제안 생성이 모두 대상. 이미지 분석은 토큰 비용이 더 클 수 있어 별도 한도 검토
- 입력 검증: URL 형식, 이미지 파일 형식/크기 제한, XSS (크롤링한 외부 콘텐츠를 그대로 렌더링할 경우)
- 클라이언트가 분석 결과를 들고 있다 저장 요청하는 구조이므로, 저장 시 서버 측 검증 필요 (태그 ID 소유권, 입력 길이 등)
