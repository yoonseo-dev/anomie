|---|---|---|
| 입력 방식 | 뉴스 URL 붙여넣기 | **URL + 책 사진 촬영, 두 방식 병행** |

## 2. 새로 추가된 사항

### 2-1. 책 스크랩 입력 경로
- 텍스트 추출 방식: **Claude Vision에 이미지를 직접 넣어 "텍스트 추출 + 개념 분석"을 한 번에 처리** (별도 OCR API 미사용)
- 원본 이미지 처리 방침: **저장하지 않음** — 정보(텍스트, 메타데이터) 정리 직후 즉시 폐기. 별도 이미지 스토리지(S3 등) 컴포넌트 불필요
- 페이지 번호: **사용자 수동 입력** (Claude Vision 자동 인식 방식은 채택하지 않음)
- 책 등록 방식: **매번 개별 입력** (표지를 먼저 등록해 책 단위로 귀속시키는 방식은 채택하지 않음 → 별도 `BOOK` 테이블 불필요)
- 테이블 구조: 뉴스 스크랩과 메타데이터 체계가 달라, 기존 `ARTICLE` 테이블을 억지로 재활용하지 않고 **`BOOK_SCRAP` 테이블로 분리**하기로 결정
  - `ARTICLE`과 각각 `TAG`와 다대다 관계를 맺으므로, `ARTICLE_TAG` 외에 `BOOK_SCRAP_TAG` 같은 연결 테이블이 별도로 필요
  - 마인드맵/전체 피드 화면에서는 두 테이블을 합쳐서(UNION 형태로) 조회해야 함 — API 설계 단계에서 처리 예정

### 2-2. 개념 간 관계(지식 그래프) 기능
- 목적: 누적된 스크랩 정보를 **마인드맵 형태로 전체 정리**할 수 있게 함
- 구조 방향: 단순히 "같은 스크랩에 같이 등장했다"는 간접 연결이 아니라, **개념과 개념 사이의 직접적인 관계를 저장**하는 방식으로 결정
- 신규 테이블(가칭): **`CONCEPT_RELATION`**
  - `sourceTagId`, `targetTagId`, `reason`(관계 설명), `status`(제안/승인) 등을 포함
- 관계 생성 주체: **Claude가 관계를 "제안"하고, 사용자가 승인/수정/삭제하는 방식**으로 결정 (Claude 전량 자동 생성도, 완전 수동도 아닌 중간 방식)
- 관계 분류 체계: **정형 카테고리 없이 자유 서술(reason 텍스트)로 우선 시작.** 스크랩이 쌓여 관계 패턴이 보이면 그때 카테고리 역추출하는 방향으로 결정 (지금 미리 정의하지 않음)
- 방향성: **무방향**으로 결정. A—B는 방향 구분 없이 하나의 연결로 취급 (인과/파생 뉘앙스는 `reason` 텍스트 서술로만 표현)
- 제안-승인 UI/UX: **마인드맵 그래프 안에 함께 표시**하는 방식으로 결정
  - 승인된 관계 = 실선, 제안(대기) 상태 관계 = 점선
  - 점선을 누르면 승인/거절 가능
  - 별도의 "제안함" 화면이나 알림 뱃지 방식은 채택하지 않음

## 3. 아직 결정되지 않은 사항

- 없음 — 최초 정리 시점(2026-09-17)의 미결 사항 4가지 모두 확정됨
- 다음 단계: `ARTICLE`, `BOOK_SCRAP`, `TAG`, `ARTICLE_TAG`, `BOOK_SCRAP_TAG`, `CONCEPT_RELATION` 등 구체적 필드까지 포함한 schema.prisma 설계

## 4. 변경되지 않고 유지되는 사항

- 기술 스택: Node.js + Express + Prisma + PostgreSQL(Docker), Flutter + Riverpod + dio + go_router
- AI 분석 엔진: Claude API
- 인증: JWT
- 기존 `USER`, `TAG` 테이블의 기본 골격 및 역할
- URL 스크랩 경로(뉴스 기사 분석) 자체는 그대로 유지, 신규 기능이 이를 대체하지 않고 병행
