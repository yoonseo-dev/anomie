# Anomie 기획 변경사항 정리
(2026-09-30 재갱신 — 최초 2026-09-17 논의 기준)

---

## 1. 변경된 핵심 컨셉

| 항목 | 기존 기획 | 변경 후 |
|---|---|---|
| 입력 방식 | 뉴스 URL 붙여넣기 | **URL + 책 사진 촬영, 두 방식 병행** |
| 처리 파이프라인 | URL → 크롤링(Cheerio/Puppeteer) → 본문 추출 → Claude 분석 | 책 경로 신설: 사진 → 텍스트 추출 → Claude 분석 (URL 경로는 기존 그대로 유지) |
| 태그 간 관계 | 없음 (스크랩-태그 연결만 존재) | **개념(태그)끼리도 관계를 갖는 지식 그래프 구조로 확장** |
| 스크랩 테이블 구조 | `ARTICLE` 단일 테이블 | **`ARTICLE`(뉴스)과 `BOOK_SCRAP`(책) 분리** |
| 태그 저장 방식 | Claude 분석 결과를 그대로 저장 | **Claude가 태그를 "제안"하고 사용자가 승인한 뒤 저장** |
| 태그 소유 범위 | 전역(모든 사용자 공유) | **사용자별** |

## 2. 새로 추가된 사항

### 2-1. 책 스크랩 입력 경로
- 텍스트 추출 방식: **Claude Vision에 이미지를 직접 넣어 "텍스트 추출 + 개념 분석"을 한 번에 처리** (별도 OCR API 미사용)
- 원본 이미지 처리 방침: **저장하지 않음** — 정보(텍스트, 메타데이터) 정리 직후 즉시 폐기. 별도 이미지 스토리지(S3 등) 컴포넌트 불필요
- 페이지 번호: **사용자 수동 입력** (Claude Vision 자동 인식 방식은 채택하지 않음)
- 책 등록 방식: **매번 개별 입력** (표지를 먼저 등록해 책 단위로 귀속시키는 방식은 채택하지 않음 → 별도 `BOOK` 테이블 불필요)
- 테이블 구조: 뉴스 스크랩과 메타데이터 체계가 달라, 기존 `ARTICLE` 테이블을 억지로 재활용하지 않고 **`BOOK_SCRAP` 테이블로 분리**하기로 결정
  - `ARTICLE`과 각각 `TAG`와 다대다 관계를 맺으므로, `ARTICLE_TAG` 외에 `BOOK_SCRAP_TAG` 같은 연결 테이블이 별도로 필요
  - 마인드맵/전체 피드 화면에서는 두 테이블을 합쳐서(UNION 형태로) 조회해야 함 — API 설계 단계에서 처리 예정

### 2-2. 개념 간 관계(지식 그래프) 기능
- 목적: 누적된 스크랩 정보를 **마인드맵 형태로 전체 정리**할 수 있게 함
- 구조 방향: 단순히 "같은 스크랩에 같이 등장했다"는 간접 연결이 아니라, **개념과 개념 사이의 직접적인 관계를 저장**하는 방식으로 결정
- 신규 테이블(가칭): **`CONCEPT_RELATION`**
  - `sourceTagId`, `targetTagId`, `reason`(관계 설명), `status`(제안/승인) 등을 포함
  - 태그가 사용자별이므로 태그를 통해 소유자가 정해짐 → **`CONCEPT_RELATION`에 `userId`를 따로 두지 않음**
- 관계 생성 주체: **Claude가 관계를 "제안"하고, 사용자가 승인/수정/삭제하는 방식**으로 결정 (Claude 전량 자동 생성도, 완전 수동도 아닌 중간 방식)
- 관계 분류 체계: **정형 카테고리 없이 자유 서술(reason 텍스트)로 우선 시작.** 스크랩이 쌓여 관계 패턴이 보이면 그때 카테고리 역추출하는 방향으로 결정 (지금 미리 정의하지 않음)
- 방향성: **무방향**으로 결정. A—B는 방향 구분 없이 하나의 연결로 취급 (인과/파생 뉘앙스는 `reason` 텍스트 서술로만 표현)
- 제안-승인 UI/UX: **마인드맵 그래프 안에 함께 표시**하는 방식으로 결정
  - 승인된 관계 = 실선, 제안(대기) 상태 관계 = 점선
  - 점선을 누르면 승인/거절 가능
  - 별도의 "제안함" 화면이나 알림 뱃지 방식은 채택하지 않음

### 2-3. 스크랩 저장 플로우 (태그 승인 → 관계 제안) — 09-30 추가
- 전체 흐름: **스크랩 입력 → Claude 분석 → 태그 제안 → 사용자 승인 → 스크랩·태그 저장 → 관계 제안 생성 → 마인드맵에서 승인**
- 태그와 관계 모두 "제안 → 승인" 구조로 통일 (설계 철학 일관성 확보)
- 승인 전 분석 결과 보관: **앱(클라이언트)이 들고 있다가 승인 시 한 번에 저장**
  - 승인 전 앱이 꺼지면 결과가 사라지는 한계를 감수 (책 스크랩은 재촬영 필요)
  - 유실이 실제로 불편해지면 그때 서버 DB의 "임시" 상태 저장 방식으로 전환 검토
- 관계 제안 생성 시점: **태그 승인 직후 서버가 백그라운드로 생성**
  - 태그 저장은 즉시 완료 처리, 사용자는 Claude 호출을 연속으로 기다리지 않음
  - 생성된 제안은 마인드맵에 점선으로 나타남

### 2-4. 태그 소유 범위: 사용자별 — 09-30 추가
- **처음부터 사용자별 태그**로 결정 (전역 태그 후 전환은 데이터 축적 뒤에 어려워지고, 태그 수정 시 다른 사용자에게 영향이 가는 문제가 있어 배제)
- 스키마 영향:
  - `TAG`에 `userId` 추가
  - 태그 이름의 유일성 기준을 "전체"가 아니라 **"사용자 안에서 유일"**로 변경
- 감수하는 트레이드오프: 같은 개념이 사용자 수만큼 중복 저장됨, 사용자 간 공유 기능은 현재 계획 없음

### 2-5. 태그 중복 방지 전략 — 09-30 추가
- 태그 제안 시 **해당 사용자의 기존 태그 목록을 Claude에 함께 전달**
- Claude는 태그마다 **"기존 태그 중 하나(ID로 지정)" 또는 "새 태그(이름 제시)"** 중 하나로 응답 → 서버는 문자열 비교 없이 ID로 정확히 연결하고, 재사용 실패(새 태그 생성) 횟수를 로그로 집계 가능
- 방어선:
  1. **승인 화면에서 새 태그 제안 시 "비슷한 기존 태그"를 함께 표시** → 사용자가 그 자리에서 중복을 걸러냄
  2. **태그 병합 기능**(쌓인 중복을 사용자가 합치는 기능) — 후순위
- 임베딩(의미 유사도) 자동 판별은 **현 단계에서 도입하지 않음.** 위 방어선이 부족하다고 실측된 뒤 재검토
- 검증 계획: 서버 구현 후 **실제 기사 10~20개로 태그 재사용 정확도를 측정**

### 2-6. DB / 도구 판단 — 09-30 추가
- **PostgreSQL + Prisma 그대로 유지** (그래프 DB 등 별도 DB 도입하지 않음)
  - 마인드맵 조회는 "사용자의 태그 전체 + 관계 전체" 수준의 단순 조회로, 다단계 그래프 탐색이 필요 없음
  - `ARTICLE` + `BOOK_SCRAP` UNION 조회는 Prisma 기본 문법으로 어려우므로 **직접 SQL 작성 또는 두 번 조회 후 서버에서 병합**으로 처리
- 기존 진행 사항(`schema.prisma` 작성 완료, docker-compose 작성 중)은 **기획 변경 전 기준**
  - `schema.prisma`는 변경된 구조(7개 테이블)에 맞춰 **재작성**
  - 개발 DB에 실제 데이터가 없으므로 초기화 후 새로 적용해도 손실 없음
  - docker-compose 작업은 스키마와 무관하므로 그대로 진행

## 3. 아직 결정되지 않은 사항

- 7개 테이블의 구체적 필드 설계 — 이번 논의에서 초안을 제시하고 검토하는 방식으로 진행 예정
  - 대상: `USER`, `TAG`(userId 추가), `ARTICLE`, `BOOK_SCRAP`, `ARTICLE_TAG`, `BOOK_SCRAP_TAG`, `CONCEPT_RELATION`
- 태그 병합 기능의 도입 시점 (후순위)
- 승인 전 분석 결과 유실 대응의 서버 임시 저장 전환 시점 (불편해지면 검토)

## 4. 변경되지 않고 유지되는 사항

- 기술 스택: Node.js + Express + Prisma + PostgreSQL(Docker), Flutter + Riverpod + dio + go_router
- AI 분석 엔진: Claude API
- 인증: JWT
- 기존 `USER`, `TAG` 테이블의 기본 골격 및 역할 (단, `TAG`에 `userId` 추가)
- URL 스크랩 경로(뉴스 기사 분석) 자체는 그대로 유지, 신규 기능이 이를 대체하지 않고 병행
